# 개발·검증 기준

작은 사용자 기능을 요구사항 → 계약·상태 → 핵심 로직 → 저장소·외부 연동 → 진입점·화면 → 검증 순서로 완성한다.
화면이 보인다는 이유만으로 기능 완료로 판단하지 않는다. 작은 저장소에 불필요한 모노레포 구조를 강제하지 않는다.
규모가 필요한 경우 apps(진입점), modules(업무 규칙), integrations(외부 구현), shared(검증된 공통 계약)로 책임을 분리한다.
모듈은 공개 API로 연결하고 외부 SDK 세부 타입이 핵심 규칙에 침투하지 않게 한다.

외부 연동은 port → fake → real adapter → contract 검증 → 승인된 sandbox/운영 검증 순으로 진행한다.
fake 성공은 실제 서비스 검증 완료를 뜻하지 않는다. 구현, fake 검증, sandbox 검증, 운영 검증 상태를 구분한다.

## 프로젝트별 검증 명령

실제 저장소에 존재하는 명령으로 채운다. 없는 명령은 임의로 성공 처리하지 않는다.

| 항목 | 명령 | 적용 조건 |
|---|---|---|
| 변경 범위 검사 | 미설정 | 모든 변경 |
| lint / typecheck | 미설정 | 해당 기술을 사용할 때 |
| 단위 / contract 테스트 | 미설정 | 로직·연동 변경 |
| 통합 / E2E | 미설정 | 사용자 흐름·경계 변경 |
| production build | 미설정 | 빌드·배포 영향 |
| migration / 접근 정책 / rollback | 미설정 | 데이터·권한 변경 |

검증은 변경 위험에 맞춘다. 정상뿐 아니라 오류·권한·빈 상태·중복·동시성·복구를 필요한 범위에서 확인한다.
UI 변경은 실제 화면과 반응형·키보드 동작을 확인한다. 실제 외부 발송·결제·운영 데이터 변경은 승인된 범위에서 수행한다.

## 요구사항과 증거

| 요구 ID | 기대 동작 | 담당 태스크 | 검증 방법 | 실제 상태·환경 | 증거 위치 |
|---|---|---|---|---|---|

실패·미실행·외부 대기는 원인·책임자·해제 조건을 남긴다. 운영 완료가 필요한 기능을 로컬 테스트만으로 완료 표시하지 않는다.
